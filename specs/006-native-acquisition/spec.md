## Clarifications and boundaries

### Established direction

The owner requested this S6 specification in parallel with S2 and S3. The native producer is first-party Rust; dependency selection belongs to the owner and the plan, not these requirements. S1 remains the authority for canonicalization, exact and near-duplicate grouping, chunking, representations, embedding and verified publication. S6 supplies acquisition, extraction and their receipts, not alternative downstream engines.

“Any data type, any structure” means content-based type detection and a single extensible profile registry governing every document. A new type or structure adds a manifest profile and, only when necessary, an extractor plug-in behind the existing port, never a core-code change. Unqualified content still yields safely obtainable text, metadata and an asset record with explicit partial/unsupported status; it is never silently dropped or falsely called fully extracted. Safely obtaining a text layer does not qualify it for publication. Images, audio and video are first-class registry entries whose derived outputs need qualification. The required qualification matrix below is the initial acceptance inventory, not a closed list of allowed types.

The pipeline infers document structure from an approved new source or sample and writes evidence-backed proposed profiles, cleanup rules, chunking strategy, deduplication keys and exclusions into that collection's manifest section. Every run detects drift and proposes adaptations. The manifest is the single configuration authority; automatic inference cannot create an independent hidden rule store.

“Perfectly done” means explicit measurable gates, retained losses and refusals, and no silent corruption, omission or authorization bypass. It is not a claim of universal accuracy on unseen content.

### Owner decisions and retained supervisor boundaries, 2026-09-30

The later owner instruction, “yes automatic, harvesting can run in parallel without collision, I don't want you to wait for the other deliveries,” supersedes the earlier proposal to gate live connectors and schedules on S3/S4.

1. **Independent S6 — decided:** S6 depends on S1, not S3 or S4 delivery. Small policy-source, connector and scheduling ports have local adapters now: direct manifest-file policy, supervised subprocess connectors speaking the shared extension protocol, and command-line/timer invocation. Later S3 catalog and S4 host/scheduler adapters replace these without caller changes. This is not a second general extension host or workflow runtime; required isolation and authority checks still apply before live execution.
2. **Automatic adaptation — decided:** Only selected profiles, cleanup rules, S1 chunking strategy within the qualified model limit, dedup keys, and new `exclude_from_knowledge` or `asset_only` entries may change automatically. Passing the fixed mandatory gate matrix activates these changes and produces a private report. Every other configuration field requires separate approval; a mixed proposal is held in full, never partially applied. Failed or inconclusive gates also hold the proposal; approval cannot bypass a mandatory gate.
3. **Parallel harvesting — decided:** Sources/families share one frontier with no duplicate in-flight fetches, aggregate per-origin politeness, idempotent captures, isolated per-run staging and S1 atomic publication. CPU, GPU and storage budgets are manifest-configurable; ingestion yields resources to interactive work.
4. **Internal wikis — approved 2026-09-30:** One named origin at a time, with owner approval and expiry. The OA2 architecture amendment may proceed; live activation still needs that exact-origin authenticated grant and qualified enforcement. There is no global “allow private network” switch. Product mappings remain declarative manifest data.
5. **Quality — approved 2026-09-30:** Q1–Q5 and the fixed matrix/protocol below, including **δ = 0.01** for nondeterministic retrieval. Approval fixes the bar; it is not a passing result.

### Approved operational defaults (OA3, 2026-09-30)

These are approved operating bounds, **not measured capacity or source grants**. A missing or unenforceable bound blocks the affected work. Stricter origin, grant and host limits win: ceilings compose with **min**, protected floors (free space, VRAM headroom, minimum request interval and other “at least” values) with **max**. Incompatible bounds hold/pause rather than weaken one side.

| Envelope | Approved default |
| --- | --- |
| Concurrency and network | **4 source runs** total; **1 in-flight request/origin**, aggregate **1 request/second/origin**; **2 retries** with at most **60 seconds** backoff; longer required server delay leaves work pending. Manual sync by default; explicitly enabled timer cadence **24 hours**. |
| CPU, memory and GPU | Aggregate **3 CPU cores**, **8 GiB RAM**; per run **2 cores / 4 GiB RAM** under the aggregate cap. **1 ingestion GPU batch** at a time, VRAM at most **min(8 GiB, currently free VRAM minus 2 GiB reserve)**; insufficient headroom pauses ingestion. No interactive model eviction. |
| Disk and staging | At most **10 GiB temporary/staging data per run, 20 GiB aggregate**; reserve **30 GiB free backing-store space** before and during writes. Checkpoint/pause before the reserve would be crossed. Larger assets require a separately approved envelope. |
| Per-document decoding | **256 MiB expanded bytes**, **100:1 expansion ratio**, **4 nested container levels**, **1,000 members**, **32 million decoded pixels**, **120 seconds**, **2 GiB memory**; XML entity expansion and external entity retrieval **disabled**. Limits apply to every step and cumulative document expansion. |
| Sampling and adaptation | Initial sample **30 documents**, bounded by OA4c. ## User Scenarios & Testing *(mandatory)*

### User Story 1 — Approve and acquire a public source (Priority: P1) MVP

As a collection owner, I declare approved origins, entry points and exclusions, preview what is eligible, and acquire a public documentation source without an authenticated connector or orchestration runtime.

**Why this priority**: It proves the admission-to-capture boundary without private accounts and prevents a broad crawl being the first test.

**Independent Test**: Use a synthetic public-document site with an allowed path, a denied neighbour, robots rules, redirects and an attached document. Run manual full sync through the public built-in adapter with the extension host unavailable.

**Acceptance Scenarios**:

1. **Given** a checked executable policy and caller grant, **When** sync starts, **Then** every attempted request has a policy decision and every discovered item has a durable disposition and capture or reason for absence.
2. **Given** a seed excluded by policy or robots, **When** it is submitted directly, discovered, retried or resumed, **Then** zero requests reach that denied destination.
3. **Given** a missing exclusion registry, unknown field or review-only proposal, **When** admission runs, **Then** it refuses before network access.
4. **Given** no S3 install or S4 host, **When** the owner uses a locally authorized executable policy, **Then** public manual sync still works; it claims neither trusted catalog installation nor extension activation.

### User Story 2 — Preserve a document through embedding (Priority: P1)

As a knowledge user, I need commands, tables, warnings, versions and citations to survive extraction so a retrieved passage says what the source said.

**Why this priority**: More documents do not help if conversion changes technical meaning.

**Independent Test**: Submit synthetic captures for every required media profile, including nested tables, literal code, scanned pages and malformed neighbours. Follow accepted outputs through the existing S1 pipeline into a scratch generation.

**Acceptance Scenarios**:

1. **Given** a supported document, **When** extraction finishes, **Then** immutable source bytes, extracted Markdown, structural mappings and a fidelity receipt link to the resulting canonical revision and chunks.
2. **Given** a lost table cell, changed command or unreadable page, **When** the fidelity gate runs, **Then** the document is held with the loss; extracted text alone cannot make it pass.
3. **Given** identical content at two approved sources with different access, **When** S1 groups it, **Then** processing is shared only under S1's contract and both source occurrences and permissions remain distinct.
4. **Given** an unsupported attachment, **When** it is captured, **Then** safely obtainable text/metadata, its bounded asset and reason remain inspectable as partial/unsupported; no empty document or invented description enters embedding.
5. **Given** a missing qualified embedding profile or a failed batch, **When** publication is requested, **Then** work remains resumable and the prior verified generation remains current.

### User Story 3 — Configure a new source and adapt safely (Priority: P1)

As a collection owner, I give the pipeline an approved source or bounded sample rather than hand-writing a product mapping. It learns a proposed processing configuration, verifies it, applies passing changes automatically and explains every change.

**Why this priority**: New content types and changing layouts must not require a core release or silently degrade the index.

**Independent Test**: Supply two unrelated synthetic sources with different structures, misleading extensions and unqualified media. Change one source's layout, duplicate rate and table structure on a later run. Observe manifest proposals, gate results, automatic activation or a held proposal, and the still-usable prior index.

**Acceptance Scenarios**:

1. **Given** an approved bounded sample, **When** profiling runs, **Then** it identifies kinds, headings/sections, tables/code, boilerplate/navigation, language, duplicate/version families and alias candidates, with evidence and uncertainty for each proposed rule.
2. **Given** a previously unknown type or structure, **When** a profile and optional extractor plug-in are registered, **Then** core callers do not change; safe text/metadata and an asset record remain available as partial/unsupported until qualification succeeds.
3. **Given** an allow-listed candidate passing the fixed mandatory gate matrix, **When** its activation is committed, **Then** the manifest's active version changes automatically with an old/new diff, evidence and rollback reference, and the owner can inspect its visibility-scoped local report.
4. **Given** a missing/failed gate, ambiguous inference or conflicting manifest edit, **When** adaptation is attempted, **Then** the candidate stays proposed for approval and the last qualified configuration/index stays active.
5. **Given** drift during concurrent harvests, **When** one source proposes a change, **Then** other runs retain their pinned configuration; changed authority is still enforced immediately and no stale proposal overwrites a newer manifest.

### User Story 4 — Refresh, resume, withdraw and repair (Priority: P1)

As an operator, I need changed material to appear once, failed work to remain pending, and withdrawn or corrupt material to stop being served.

**Why this priority**: The migration is unsafe unless routine maintenance is as reliable as the first crawl.

**Independent Test**: Drive the same synthetic source through full and incremental runs, interruption, a changed link with unchanged text, permission narrowing, withdrawal, and deletion of a local artifact. Compare with an uninterrupted reference run.

**Acceptance Scenarios**:

1. **Given** a capped or unstable enumeration, **When** the run stops, **Then** coverage is partial, unfinished partitions remain pending, and their watermark does not advance.
2. **Given** a crash after a capture but before stage completion, **When** resume runs, **Then** current policy is checked again and completed verified work is reused without duplicate visible occurrences.
3. **Given** temporary authentication failure, **When** reconciliation runs, **Then** absence is not treated as deletion; a proven withdrawal or new exclusion instead invalidates affected access and derivatives.
4. **Given** an unchanged repository commit but a missing local tree, **When** repair runs, **Then** integrity failure causes reacquisition rather than a false unchanged result.
5. **Given** an extractor/profile change, **When** repair runs, **Then** it creates new derivatives from retained captures without rewriting original evidence or using stale outputs as current.

### User Story 5 — Connect a private source or wiki safely (Priority: P2)

As an authorized operator, I connect vendor documentation, a knowledge base, community or internal wiki without giving the generic engine vendor-specific logic or exposing credentials.

**Why this priority**: Protected sources need proven generic admission and capture behavior before live access.

**Independent Test**: With synthetic identity/session services and the local supervised subprocess adapter, activate two collections with different account bindings while S3/S4 are unavailable. Exercise wrong-account refusal, session reuse, expiry, human challenge, declarative wiki pagination and permissions, then deactivate the connector.

**Acceptance Scenarios**:

1. **Given** a valid session, **When** a protected request starts, **Then** the session is checked before credentials are requested and no secret appears in receipts, arguments or diagnostics.
2. **Given** missing activation authority, the wrong account, an owned-profile conflict or human-required challenge, **When** acquisition starts, **Then** that source pauses or refuses without credential guessing or interference with another browser.
3. **Given** a second wiki using the same supported mapping capabilities, **When** its manifest is added, **Then** page/block identity, hierarchy, revisions, attachments, cursors and permissions work without product-specific code changes.
4. **Given** an approved private origin, **When** DNS, a redirect or a subresource targets an unapproved destination, **Then** that request is denied even if the starting page was allowed.
5. **Given** an expired policy grant or connector deactivation, **When** work resumes, **Then** no further protected request is dispatched and pending work remains durable.

### User Story 6 — Retire one legacy producer with evidence (Priority: P2)

As the owner, I replace one source family's Python producer only after I can inspect parity, quality and retrieval results and reverse the switch safely.

**Why this priority**: A family-by-family cutover avoids a migration that is all-or-nothing.

**Independent Test**: Run both producers against identical synthetic captures and a separately approved live sample, build isolated candidate generations, exercise rollback, and inspect a family cutover receipt.

**Acceptance Scenarios**:

1. **Given** a frozen family inventory, **When** comparison runs, **Then** every selected item and every discrepancy is accounted for, including full, incremental, resume, withdrawal and repair behavior.
2. **Given** a legacy defect, **When** native output differs, **Then** independent source-grounded review records the correction; matching a known defect is not parity success.
3. **Given** passing approved gates, **When** the owner switches that family, **Then** exactly one producer owns its refresh, native refresh is observed, and the previous accepted generation remains recoverable subject to current revocations.
4. **Given** any unqualified family, **When** milestone status is reported, **Then** that family remains on its previous producer and M6 is not reported complete.

### Edge Cases

#### Admission and acquisition

- Seed/path-prefix confusion, encoded separators, ambiguous queries, URL credentials, fragments, DNS rebinding and redirects through authentication endpoints: parse and check each actual destination; identity rules never act as egress permission.
- Unreadable robots, a missing/corrupt registry, expired private-network approval or narrowed grants during resume: fail closed for affected work, not a catch-all retry or cache bypass.
- Delayed rendering, a login shell returning success status, challenge pages and content-type/magic-byte disagreement: typed non-content outcomes; no false document.
- Paginated result caps, concurrent edits, clock skew and unstable totals: complete bounded partitions or an explicit incomplete window; no fictional remote snapshot.
- A signed transfer URL expires, a server ignores a range request, or validators change mid-transfer: restart/re-mint safely; never append bytes from different representations.

#### Extraction and lifecycle

- PDF scans, password protection, multi-column order, merged table cells, formulas, embedded attachments or unsupported encodings: preserve originals, qualify the applicable mapping, disclose loss or hold.
- A short valid changelog, multilingual text, identical text with different links, literal whitespace, a changed negation or version: format-aware checks; no text-length-only acceptance or semantic over-merging.
- A deletion discovered during partial enumeration, a permission loss with unchanged bytes, or a prior generation pinned by a reader: distinguish uncertain absence from withdrawal; current revocations still apply.
- A connector crash, duplicate submission, lost lease, full disk, cancellation or corrupt accepted artifact: durable pending state, fenced ownership, integrity verification and safe repair; no silent success.
- Untrusted HTML instructions, archive links/traversal, decompression bombs, macros or external relationships: bounded isolated parsing, no execution and no undeclared network access.

## Requirements *(mandatory)*

### Functional Requirements

#### Approval and source policy

- **FR-S6-001**: Acquisition MUST require a checked versioned collection and executable source policy, current caller/source authority, required bindings and finite budgets before effects. A declaration can narrow authority but cannot grant entitlement. Questions MUST NOT trigger acquisition.
- **FR-S6-002**: The collection's source-policy section MUST occupy the requested capability hierarchy and declare approved origins, seeds, discovery/crawl selection, exclusions with reasons, promotion decisions, robots/rate rules and URL identity as specified below. Real private URLs and bindings MUST remain in the private manifest.
- **FR-S6-003**: Collection, policy, registry, acquisition-profile and wiki-mapping inputs MUST use strict versioned JSON with bounded size/depth/counts. Unknown or duplicate keys, wrong types, duplicate IDs, unresolved references, contradictory rules, invalid URLs and non-finite budgets MUST refuse. Registry admission is separately governed by FR-S6-050.
- **FR-S6-004**: Admission MUST apply caller authority and bindings, then URL/network/robots/denials, then separate content-promotion decisions, then any explicit cache-bypass rule. Denial MUST defeat a seed, redirect, subresource, resume or retry. Cache bypass MUST NOT bypass any other control.
- **FR-S6-005**: URL identity MUST preserve meaningful query semantics, use exact HTTPS origin and path boundaries, reject user information/control characters, and distinguish fetch identity from display links and signed transfer URLs. Unknown query semantics MUST refuse rather than merge identities. Identity migrations MUST be versioned and retain old-to-new mappings.
- **FR-S6-006**: Every connection/request/redirect MUST pass the versioned address-classification contract below, derived from the IANA IPv4/IPv6 special-purpose registries. Default denial includes private, loopback, link-local, unspecified, CGNAT, ULA, multicast, reserved and metadata destinations, including mapped/embedded forms. Only an OA2-approved exact-origin grant may permit its specified private-unicast ranges; no other denied class is overridden. The transport MUST connect to the exact checked address without a second resolution and ignore ambient proxy settings. Browser-channel enforcement and origin-bound credentials are separate requirements FR-S6-051–052.
- **FR-S6-007**: Robots behavior MUST follow RFC 9309 matching and fail closed when rules cannot be read. Overrides MUST be explicit source-scoped records approved by the collection owner through OA4b, including site-operator permission where required, never automatic retries. Per-origin concurrency/pacing, request and retry budgets, bounded backoff and applicable retry delays MUST be enforced across all transports.
- **FR-S6-008**: The policy-source contract MUST support direct manifest-file operation now and later S3 catalog carriage/verification of the same collection/policy and registry digests, without a second runtime authority. The later adapter is not an M6 delivery prerequisite. Policy installation MUST NOT activate a connector or widen grants. Public and authorized private sync MUST use the same validator and admission port regardless of policy-source adapter.

#### Durable acquisition and connectors

- **FR-S6-009**: S6 MUST add the kernel-owned frontier and reuse existing kernel jobs, artifacts and journal. One fenced writer lease per source MUST prevent concurrent ownership and stale submissions; connectors MUST lease work and submit verified results rather than keep a competing authoritative queue.
- **FR-S6-010**: Full mode MUST revalidate all known in-scope items and discover new ones. Incremental mode MUST enumerate complete change windows with declared overlap/skew and source-specific revision signals, verifying oldest outstanding items first. Resume MUST reapply current authority/policy. Withdrawal and repair MUST be explicit supported operations, not inferred success states.
- **FR-S6-011**: Discovery MUST durably hand every eligible discovered item to acquisition, including links from captures whose visible text is unchanged. Entitlement-scoped indexes, APIs and bounded partitions MUST prove their coverage; keyword search and identifier guessing MUST NOT stand in for enumeration. Unsplittable/unstable/capped windows MUST remain incomplete.
- **FR-S6-012**: Change detection MUST include source revisions, validators, metadata, permissions, links and representation digests as applicable, not text-only hashes. A watermark MUST advance only for fully covered, committed partitions; failed or pending items MUST NOT be marked visited or accepted.
- **FR-S6-013**: Direct requests, real-browser requests and rendered-page acquisition MUST share admission, capture and budget contracts. Every source MUST select a digest-bound acquisition profile declaring `http`, `browser_request` or `browser_render`, an installed replaceable adapter reference and required capabilities; rendered profiles MUST declare finite, bounded, non-executable readiness predicates and deadlines. Selection and readiness MUST be strict schema fields, not hard-coded caller choices. Unavoidable browser work MUST use the named out-of-process crawl4ai exception, not Spider's chromey path; it conveys no authority to extract, enqueue or publish independently. Public unauthenticated sources MUST run through a built-in adapter under the manual sync operation without an extension host; private sources MUST use the local qualified subprocess connector adapter without waiting for S4. Unsupported transport capabilities MUST refuse rather than weaken checks.
- **FR-S6-014**: Each run MUST bound attempts, pages, partitions, redirects, depth, elapsed time, response/DOM/archive bytes, storage and owned process resources. Asset and document budgets MUST be distinct. Cancellation MUST stop owned work and reap owned processes; client timeout alone MUST NOT imply cancellation. Independent sources MAY continue after another fails, but dependent stages MUST not consume unverified stale output.
- **FR-S6-015**: Every capture MUST retain immutable authorized body bytes and an envelope identifying source/item, requested/final identity, redacted redirect chain, status, safe selected headers, media type, digest, acquisition time, transport and profile. Wire body, rendered DOM, selected HTML and derived API record MUST be distinguished; none may be mislabeled as the others. Signed URLs and headers MUST be redacted so credentials are not persisted as provenance.
- **FR-S6-016**: Each run MUST retain a unique non-overwritten receipt with frozen inputs/profiles/policy, per-partition coverage and item dispositions. Counts of discovered, attempted, accepted, unchanged, denied, blocked, refused, withdrawn and pending MUST identify their stage and counting unit; attempts and stages MUST NOT be added as if disjoint items. Failed, partial and blocked work MUST be visible in machine output and MUST NOT return a successful-completion claim.
- **FR-S6-017**: Private/vendor connectors MUST remain private, replaceable source-connector extensions under ADR-0013, with explicit activation, principal and declared effects. Product-specific behavior MUST NOT enter the generic engine. Supervision, network isolation and artifact admission are separately testable under FR-S6-054–056.
- **FR-S6-018**: Authentication MUST resolve isolated account/credential/session roles and probe the session before obtaining credentials. Secrets MUST remain in an approved protected facility or protected transient memory; plaintext persistence, logs, arguments, environment variables, crash dumps, swap, capture envelopes and journal payloads MUST NOT contain them. The connector normally receives an opaque run/account-bound session handle; the admitted transport attaches origin-bound session material. If an approved connector function requires secret bytes, deliver them only over a private inherited authenticated IPC handle to non-dumpable, non-swappable memory, with bounded lifetime and cleanup; inability to enforce these protections blocks that function. Anonymous sources MUST NOT request credentials; account mismatches MUST refuse.
- **FR-S6-019**: Session handling MUST check browser/profile compatibility and ownership, preserve existing signed-in sessions without modifying another profile, and pause for human-required MFA, challenges or legal attestations. It MUST NOT guess codes, repeat challenge loops, bypass compliance or kill/unlock another browser. The first protected preflight MUST remain bounded to one source/account/target, 180 seconds, two protected reads and one login cycle, with retries disabled and redacted outcomes.
- **FR-S6-020**: Internal wiki mapping MUST be declarative, strict manifest data describing supported API/response fields, page/block identity, hierarchy, content, revisions, pagination/cursors, attachments and effective permissions. A second product using supported capabilities MUST require configuration and fixtures only, not hand-written per-product code. Unsupported semantics or missing permission mappings MUST refuse; mappings MUST NOT contain scripts or grant endpoint/network access.

Safely controlled lifecycle fixtures remain mandatory where live deletion/expiry cannot be induced. |
| **Q5 — Retrieval non-regression** | Freeze the actual current S1 generation at qualification start and re-freeze/re-run if it changes before cutover. Use golden v2.2 for its collection, otherwise that collection's approved suite. **Deterministic retrieval:** require exact equality of the primary scored metric values (Recall@5/10, MRR@10, grouped nDCG@10, delivered-section coverage, no-answer accuracy and false-abstention rate), overall and in each predefined nonempty stratum, after approved identity mapping. One paired run suffices; report every per-question outcome/rank change separately and independently review every lost question. This is metric equality, not byte equality of trace timings or a requirement that no question ever changes. **Nondeterministic retrieval:** use owner-approved non-inferiority margin **δ = 0.01 absolute** on those normalized metrics overall and predefined nonempty strata. Use three paired repetitions with a seeded question-level paired bootstrap of 2,000 resamples (repeat means per question, never repeats as independent questions); the lower 95% bound of native-minus-baseline must be ≥−δ. For false-abstention rate the upper bound must be ≤δ; no-answer accuracy uses the lower-bound rule. Every lost question requires an independent source-grounded disposition; it is not automatically forbidden, but the disposition cannot remove the question, alter gold or excuse failure of the chosen equality/non-inferiority gate. Command exactness remains 100%, scope correctness is exact, and existing S1 release/latency floors still apply. Missing baseline/gold or inconclusive intervals hold acceptance. |

Q2 counts redundant preparation as preparations beyond one per eligible exact-content/profile group divided by eligible occurrences; necessary permission-separated occurrence records are not duplication failures. Q5 uses the existing evaluator's any-hit Recall and grouped relevance semantics: relevance alternatives are not newly interpreted as required multipart answers. Pin suite digest, expected-reference mapping, full generation manifests, selected models, retrieval settings, authorization context, binary and reference hardware. Compare a legacy-input and native-input generation under identical downstream S1 settings to isolate ingestion effects. Record route-level metrics before fusion, final evidence, per-query losses and latency/degraded cohorts; counts alone cannot prove retrieval quality.

## Out of Scope

1. A new canonicalizer, deduplication engine, chunker, embedder selector, index authority or retrieval-ranking redesign. S2 graph entity resolution and S7 semantic code intelligence remain separately owned.
2. Crawling during questions, identifier brute force, access-control/challenge bypass, automated legal attestations, unrestricted private-network access or embedding unknown media as fabricated prose.
3. Public vendor connectors, licensed corpora, real private URL lists, golden questions or protected account/session data. Ordinary catalog metadata is not authority to access them.
4. A duplicate general daemon, extension host, scheduler or catalog trust path. Local direct-file, supervised subprocess and command/timer adapters are in scope now. Configuration auto-application is decided; connector activation and authority grants remain separately controlled. Optional interpretation, unqualified wiki capabilities and installer document extraction retain their named approvals.
5. A big-bang legacy rewrite, a native wrapper around Python extraction/production presented as retirement, or retiring comparison evidence. A retained legacy comparison tool is not a production producer. Only FR-S6-060's named crawl4ai render-only exception can remain at M6; any other production Python path blocks cutover.

## Assumptions

- The S1 integration branch supplies the downstream contracts; completion of S6 is not evidence that S1's existing qualification gaps have been closed. Missing required S1 evidence blocks the dependent gate.
- S6 ships local adapters and live/scheduled operation independently of S3/S4. Their future adapters share the same contracts; contract conformance is not permission to omit required local isolation, authorization or resource controls.
- Every required media row is a qualification obligation; exact subformats and eligible source inventories are frozen under OA1/OA4 before tests. Optional image/audio/video interpretation is not implied by the word “capture.”
- Policy-controlled private source bodies may be retained only under their approved data classification and retention rules. Suspected secrets are quarantined in protected storage; authentication material is not made a provenance artifact. Missing retention authority blocks retention rather than choosing an invented lifetime.
- This work read existing public architecture/specifications and the lane's shared brief, not private corpora, credential stores or live protected sites. Private notes contain source-specific coordination only. Real connector qualification, live sampling and golden-v2.2 evaluation require separate authorization and were not performed.
